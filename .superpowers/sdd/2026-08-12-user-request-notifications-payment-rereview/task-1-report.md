## Self-review

### Producers

- Support ticket creation queues `support_ticket` in the same transaction as ticket and initial message creation.
- User support replies queue `support_user_message` in the same transaction as message creation and ticket status update.
- The support helper explicitly excludes admin/non-owner authors; no support message body enters the payload.
- Course application creation queues `course_application` in the same transaction as application creation and profile synchronization.
- Receipt submission replaces the previous best-effort direct Bale message with `payment_receipt` in the payment transaction.
- Profile events are queued only when the existing meaningful profile-content comparison detects a revision; password, newsletter, notification preferences, and visibility-only edits do not queue events. District, neighborhood, university, and university-field changes are included in meaningful content detection.
- Avatar submission queues `avatar_review` in the same transaction as superseding old submissions and creating the new submission.
- Every producer awaits outbox insertion, so insertion failure rejects the transaction rather than committing the request transition.

### Privacy

- Request payloads contain only display name, category-specific title/order labels, submission time, and internal identifiers needed for allowlisted admin actions.
- Support payloads contain display name and ticket subject only, never message body.
- Payload validators require exact keys and quarantine additional fields.
- Tests cover exclusion of message body, phone, email, national code, address, custom responses, upload/receipt URLs, card data, arbitrary URLs, callback data, and tokens.

### Idempotency

- Ticket, support-message, course-application, and avatar event keys use their durable database IDs.
- Superseded by Fix Round 1: receipt events use the order ID plus a durable integer submission revision, not a generated UUID or timestamp key.
- Profile events use the user ID plus a generated revision UUID only after a meaningful content change enters pending review.
- All queues use `upsert` with an empty update, preserving the first immutable payload for a repeated durable key.
- Existing payment-paid, duplicate-payment, release, retry, claim, and uncertain-delivery behavior remains covered by the full suite.

### Buttons

- Payloads contain no URLs or callback instructions.
- Event types map to a closed action union: support ticket, course application, payment order, and user.
- Dispatcher maps those identifiers to `/admin/support`, `/admin/applications`, `/admin/payments`, and `/admin/users` only.
- URLs derive from the repository canonical `NEXT_PUBLIC_MAIN_SITE_URL` convention; no production hostname was added.
- `sendMessage` independently rejects cross-origin, malformed, fragment-bearing, or non-allowlisted inline URLs before contacting Bale.
- Buttons use `reply_markup.inline_keyboard` URL entries only; no callback, approval, or rejection action exists.
